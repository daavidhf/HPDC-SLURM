## 1. Introduction
The objective of this assignment is to design and implement an automated workflow orchestrator in Python, capable of managing job executions in a High-Performance Computing (HPC) environment using the SLURM workload manager.

The workflow consists of two dependent phases:
1. **Computation Phase (Job Array):** Distributed calculation of prime numbers by dividing the total range into sub-intervals.
2. **Consolidation Phase:** A dependent job that collects the partial results and generates a single sorted output file. This phase is only executed once the computation phase finishes successfully.

## 2. Architecture and Directory Structure
Following the assignment specifications, the orchestrator can operate either in a parametrized working directory passed as an argument, or use the directory where it is located as the working directory if no argument is passed.

The dynamically managed directory structure is as follows:
* `/data`: The primary input source. It contains a hierarchical structure of undetermined subdirectories (`sample_1`, `sample_2`, ..., `sample_*`) where the numerical intervals are defined. The orchestrator scans these folders for `ranges_*.txt` files to compile the master task list.
* `/logs`: The central repository for all runtime data. It stores the orchestrator's master log (`ORCHEST_LOG.txt`) and the SLURM's standard output and error files (`.out`, `.err`). This version uses the `.out` files as the primary source for partial results.
* `/results`: The directory where final outputs and shared tsk list are stored. It contains the unified `ALL_PRIMES.txt` file and the generated `all_intervals.txt` useb by the Job Array.
* `/scripts`: Contains the source code, including the SLURM templates generated by the orchestrator (`compute_primes.sh`, `marge_primes.sh`) and the auxiliary source code to operate with the data (`count_tot_primes.py` and `consolidate_results.py`).

*Note: At the beggining of each execution, the orchestrator includes a cleanup routine to delete previous executions from the logs folder, ensuring a clean environment.*


## 3. Implementation Details (Python)
The orchestrator is divided into four phases:

### 3.1. Cleaning Previous Results/Logs and System Logging Configuration
All previous logs (`.out`, `.err`) from the last execution are deleted, and the `ORCHEST_LOG.txt` is cleaned up.
An auxiliar function is designed to print messages in the `ORCHEST_LOG.txt` with the real-time in which are printed.

### 3.2. Data Folders Analysis and Tasks Preparation
The hierarchical structure of source data subdirectories (`/data/sample_*`) is analized to extract the intervals defined inside each file (`/data/sample_*/ranges_*.txt`), and a master task list with all of them is stored (`/results/all_intervals.txt`).

### 3.3. SLURM Generation and Submission
1. **Computation Phase (Job Array):**
A SLURM Bash script has been designed to run the `count_tot_primes.py` script in parallel, using an array with as many subtasks as there are intervals in the `all_intervals.txt` file. `--ouptut` and `--error` flags have been configured to create the `compute_JobID_IndexArray.out` and `compute_JobID_IndexArray.err` files inside the `/logs` directory.

Job Sequence:
- Extracts the line of `all_intervals.txt` corresponding to each index array.
- Separates the line content (2 numbers separated by a whitespace) into the START and END variables.
- Runs the python `count_tot_primes.py` script with the START and END variables as the arguments.
- Deletes the last line printed by the python script, which shows the total number of primes in that interval.

2. **Consolidation Phase:**
A SLURM Bash script has been designed to run the `consolidate_results.py` with the aim of merging the partial results from the intervals performed in the computation phase. `--ouptut` and `--error` flags have been configured to create the `merge_JobID.out` and `merge_JobID.err` files inside the `/logs` directory.

The `consolidate_results.py` analyzes all the partial outputs sequentially and stores the prime numbers in a `set()` class, which enables to not repeat a prime number if it has been already stored in it. Finally, it sorts the numbers stored in it in an ascending order, and finally prints the total number of primes detected (without repetitions).
The SLURM Bash script orders to generate and store the results in the `ALL_PRIMES.txt` file, which is the final file with the results.

For the communication between the orchestrator and the operating system of the access node (`aoclspv.uab.cat`), Python's `subprocess` module has been used. The `subprocess.run`function was configured with the parameters `stdout=subprocess.PIPE` and `stderr=subprocess.PIPE`. This allows the orchestrator to:
* Capture the `stdout` to dynamically extract the *Job ID* generated by SLURM when submitting the Job Array, which allows to assign the dependency between the first and second job.
* Capture the `stderr`, which combined with the `check=True` flag, any failure when invoking `sbatch`raises a `CalledProcessingError` exception, stopping the execution and logging the exact reason for the failure in the master log (`ORCHEST_LOG.txt`).

To guarantee the sequential logic of the project, the second job (consolidation) extracts the *Job ID* from the first one and is submitted to the queue using the `--dependency=afterok:<job_id>` flag. This delegates the waiting responsibility to SLURM rather than blocking the Python process.

### 3.4. Results
The third phase ends submitting the Jobs to SLURM, but this does not mean that the jobs have ended.
This final phase, which is implemented in the `consolidate_results.py` source code, prints in the `ORCHEST_LOG.txt` of the `/logs` directory that the jobs have ended, and the results have been written in `ALL_PRIMES.txt` inside the `/results` directory.

## 4. Validation
After submission, the SLURM queue was checked using the `squeue -u $USER` command. The output confirmed that the Job Array (computing phase) transitioned to the Running (R) state, while the consolidation job remained in the Pending (PD) state with the exact reason `Dependency`. This validated that SLURM successfully recognized and managed the `--dependency=afterok:<job_id>` flag.

Upon completion of the consolidation job, the `/results/ALL_PRIMES.txt` file was examined. The file contained a stricly ascending list of prime numbers with no duplicates, and the final line correctly displayed the total count.

Finally, the `ORCHEST_LOG.txt` provided a perfect chronological trace of the entire execution, from the initial directory cleanup to the sel-reported success message triggered by the `consolidate_results.py` script.

## 5. Conclusions
The development of this workflow orchestrator has successfully demonstrated how to automate and manage complex, dependent computational tasks in a High-Performance Computing environment using SLURM.

Some key architectural decisions contributed to the robustness of the system:
- By leveraging SLURM's native standard output streams (`.out`) to carry intermediate data, the system significantly reduced input and output operations, avoiding the generation of unnecessary temporary files.
- Delegating the job sequence control to SLURM rather than enforcing Python to wait, optimized the use of the access node's resources and reinforced the asynchronous nature of cluster computing.
- The use of Python's `subprocess`module with standard error capturing and exit code checking ensures that any configuration or submission failure is caught and logged, preventing silent errors.

This project solidifies the core concepts of distributed computing, automated job scheduling, and the importanc of designing location-agnostic, scalable pipelines in modern HPC ecosystems.

**Limitations and Future Work**

Despite its robustness, the current architecture presents a tight coupling with the project's internal directory tree. Even when the orchestrator is executed from an external location, it strictly mandates that the target data directory contains the auxiliary scripts within a specific `/scripts` folder. A potential improvement for future iterations would be to bundle the auxiliary scripts directly within the orchestrator's logic or implement an auto-deployment mechanism that temporarily provisions the worker nodes with the required scripts, thereby achieving complete structural decoupling.
